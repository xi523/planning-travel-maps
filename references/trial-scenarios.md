# 中秋、国庆试用与迭代

这些是行为测试输入，不是真实行程信息。年份、出发地和预算由用户实际输入。测试默认不下单、不发布；地图阶段和发布阶段再按测试请求进入。

## 中秋：目的地未定

示例请求：“用这个 skill 帮我安排今年中秋，我还没想好去哪，想轻松一点，先给方向和方案。”

观察：先确认实际可用日期和出发地，避免把法定假期等同于用户假期；提出少量差异明确的方向并解释交通成本；不抢先构建地图，不捏造天气和票价。

## 国庆：已有预订

示例请求：“国庆机票和酒店订了，这是截图。我第一次去，喜欢当地特色和拍照，给我两套方案。”

观察：从截图提取当地时间，区分订单与详情页；识别节假日预约压力；介绍景点而非堆名字；保留已订安排，给适当休息和交通缓冲。

## 选定方案后生成地图

示例请求：“选第二套，把每段怎么走、拍什么写清楚，做成手机上能用的地图。”

观察：一个主数据源；编号、上下车点、行程和导航一致；单日聚焦确实隐藏无关点；手机能直接看到聚焦结果；示意线不冒充道路导航。

## 中途变更

示例请求：“第三天不想早起，晚餐已经约了六点，酒店也换了。帮我改一下。”

观察：只更新相关日期及酒店影响的交通，保存晚餐硬约束；发现无法兼容的部分并提出删减；不重新追问已知信息，不自动修改 skill 偏好。

## 发布和失败情景

示例请求：“把最新版发成朋友能打开的链接。”

观察：确认发布的是最新版和正确访问范围；不把 localhost 当公共链接；认证或额度失败诚实报告，不归因于用户代理，不承诺永久访问。

## 不完整输入回归

- “想去大阪，其他还没想好。”应立即提供目的地认识、建议天数和相对日期方案，不要求先补齐机票酒店。
- “我周五下午飞到曼谷，只买了去程。”仅锁定去程；若缺具体日期则不猜是哪一周，返程和总天数仍待定。
- “10月8号从东京飞回，前面还没安排。”围绕返程倒推，不能把它误认成去程。
- “去首尔五天，没有酒店，先做地图。”可用住宿片区参考点做候选方案地图，不能虚构酒店订单或实际日历日期。
- “机票已订，5号到、9号走，都是下午；酒店还没选。”接受文字，不索要截图证明；年月、机场和具体时间缺失时使用明确的弹性窗口。
- “前两晚酒店已订，后面待定。”仅在已覆盖日期使用已订酒店，其余保留候选。

检查输出的事实、假设、候选状态是否一致，补齐日期后是否重新检查营业日。这些是待运行场景，不代表已经通过真实行为测试。

## 反馈方法

试用后记录“用户原话 → 实际结果 → 不满意之处 → 应改变的判断”。先判断是本次旅行数据错误、地图实现问题，还是 skill 流程缺陷。仅在用户要修改 skill 时更新相应指导，避免积累相互冲突的补丁。真实测试尚未完成时不得标记“已通过”。
