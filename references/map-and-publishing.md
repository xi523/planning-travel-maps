# 地图制作与分享

## 地图成品

复用已有地图结构；新图可用 Leaflet 等成熟地图库。不要直接复制京都真实订单、部署记录或用户数据作为模板。单文件 HTML 可嵌入行程 JSON；生成时安全序列化，避免数据中的 `</script>` 终止脚本，文本优先通过 textContent 渲染。

必需视图：全程概览、单日聚焦、适合现场查看的局部分段。聚焦时隐藏无关点和线，恢复全图入口可见；缩放后编号可辨认，图例只解释当前显示内容。手机上点击聚焦应让用户看到地图，不能只更新屏幕下方不可见的区域。

点位弹窗提供名称、介绍、预约状态、机位或入口提示、外部地图导航。区分相似分店、同名站和主景区/内部机位。行程表同时列出交通方式和估算时间。

含照片的长弹窗需根据地图高度限高、内部滚动，保持关闭按钮可达，并实际验证手机和桌面都能滑到底部导航。美食候选的图层、评分与图片遵循 [美食研究与选择](food-selection.md)。

无路由服务时画分段示意线，显式标注“顺序示意，非道路导航”，不要用“精确实走导航”命名。可验证的外部导航承担逐街道路线；景区内提供官方境内图。步行、铁路、打车样式有区分，不用同一实线暗示均可步行。

地图瓦片、脚本、图片加载失败时显示诚实的加载状态，文字攻略仍可阅读。只有把所需依赖和获准离线使用的地图资源处理好并测试后，才能声称完全离线可用。

遇到瓦片 403，检查提供方使用政策、来源信息和访问方式，不循环请求被拒绝瓦片或伪造来源绕过限制。file:// 缺少来源信息时，可使用本机 HTTP 服务并验证；仍失败则停止该底图加载，保留文字与外部导航，或选用许可适合的底图服务。

## 验证

先检查数据引用和脚本语法，再对新增交互做浏览器验证：桌面和手机文字不溢出，地图有尺寸且非空白，单日/分段过滤有效，弹窗与导航目标正确，图片真实加载，网络失败有降级。不要把 DOM 中存在地图容器当作底图加载成功。

如果浏览器不可用，完成静态检查并注明未做视觉验证；不能假称已截图检查。不必因一个可选图片失败无限重试。

## 发布流程

只有用户要求发布/分享网址时才执行；已明确授权的重复发布无需再问同一问题。

1. 找到项目内已有部署记录、站点和可用发布工具，读取对应平台当前指导。优先更新既有正式站点，不预设 Netlify、Sites 或其他平台一定可用。
2. 明确网页的可访问范围。用户要求朋友可打开，应选择符合授权的分享方式，不能把仅本人可见网址当成已完成共享。
3. 只打包实际网页和所需静态资源，不能上传整个个人工作目录、截图订单、凭证或密钥。沿用现有构建方式，无需为静态地图强行重建框架。
4. 完成必要构建/检查再上传。授权失效时仅能断言发布授权失效，不能由此推断旧网站停用原因。连接器要求重新认证时说明所需动作；换平台需要符合用户已授权的公开范围和成本限制。
5. 平台明确返回发布成功后，访问最终 URL 并核对标题和本次修改特征，必要时比较文件摘要；不要把旧页面 HTTP 200 当最新版已发布。若访问验证受限，清楚区分“平台报告成功”和“外部访问未验证”。
6. 项目内保存非敏感 `deployment.json`：平台、站点 ID、URL、访问范围、发布时间、版本摘要、验证结果和已知有效期。不保存令牌。

临时匿名部署、本机隧道和本地服务要说明时限或运行依赖。正式托管也不能承诺永久可用。对于相同错误只做有新证据的重试，账号认证、额度和权限问题需要对应修复，不能通过无限换名字绕过。

最终交付以成功验证的链接为主；失败则交付可用本地成品、明确阻塞原因及最短下一步，不捏造网址。
